# GWS (Google Workspace CLI) — Tool Reference

`gws` is a Google Workspace CLI covering Gmail, Calendar, Drive, Docs, Sheets, and admin endpoints. Authenticates via OAuth2 against a per-operator Google Cloud OAuth app whose credentials live in Infisical.

This tool layer rides on top of the Infisical foundation (`config/rules/tools/infisical.md`). Don't attempt to set up gws on a machine that hasn't run `bootstrap-infisical.sh`.

## Access Method

CLI binary: `gws`, installed by `setup-gws.sh` via `brew install googleworkspace-cli` (preferred) or `npm install -g @googleworkspace/cli` (fallback). Both methods come from the official repo at https://github.com/googleworkspace/cli — do NOT `brew install gws`, which installs an unrelated git-workspaces tool of the same name.

A shell wrapper at `config/shell/gws-env.sh` makes `gws auth login` pull the OAuth-app `client_id`/`client_secret` from Infisical at the moment of login — no env vars in your shell, no copy-pasting. Source from `~/.zshrc`:

```bash
source /path/to/Workdesk-OS/config/shell/gws-env.sh
```

The wrapper is a pass-through for every command except `gws auth login`, which it intercepts to inject the OAuth-app credentials (requires an active `infisical login` user session).

## Setup

Run once per machine, after `bootstrap-infisical.sh`:

```bash
bash config/scripts/setup-gws.sh
```

That script:
1. Verifies the Infisical user session works.
2. Installs gws if missing (`brew install googleworkspace-cli`, falling back to `npm install -g @googleworkspace/cli`).
3. Ensures `~/Library/Application Support/gws` is a real directory (repairing the legacy ramdisk symlink if one is found).
4. **If Infisical has a synced copy of your gws state** — restores it: encrypted refresh token, encryption key, `accounts.json`, and a `client_secret.json` rebuilt from the three `PERSONAL_GOOGLE_WORKSPACE_*` keys. No browser OAuth needed.
5. **If not** — walks you through `gws auth login` (browser), then a re-run of the script syncs the fresh state to Infisical.

Idempotent — re-run any time to repair drift or finish a two-pass first-auth.

## Where state lives

`gws` keeps OAuth state on disk (FileVault covers encryption at rest; sensitive files are `chmod 600`). **Two layouts exist across gws versions, and the scripts auto-detect which is present.**

### xdg layout (current — googleworkspace-cli ~0.22+) — `~/.config/gws/`

The default on current installs. The encryption key lives in the **macOS Keychain**, not a file.

| Location | What | Synced copy in Infisical |
|---|---|---|
| `~/.config/gws/client_secret.json` | OAuth app creds (client_id/secret/project_id) | Rebuilt on restore from the three `PERSONAL_GOOGLE_WORKSPACE_*` keys |
| macOS Keychain, service `gws-cli` | Per-install random key that wraps the refresh token | `PERSONAL_GWS_ENCRYPTION_KEY_B64` (base64; read needs a one-time Keychain approval, so pushed only via `gws-push-tokens-to-infisical.sh --include-keychain-key`) |
| `~/.config/gws/credentials.enc` | Encrypted OAuth refresh token (single file) | `PERSONAL_GWS_CREDENTIALS_<KEY_SUFFIX>_ENC_B64` (stored base64) |
| `~/.config/gws/account_timezone` | Small account metadata (replaces `accounts.json`) | `PERSONAL_GWS_ACCOUNT_TIMEZONE` |
| `~/.config/gws/token_cache.json` | Short-lived access token (~1h) | Not synced — regenerated by `gws` from the refresh token |

### legacy layout (older gws) — `~/Library/Application Support/gws/`

Still handled by the scripts if present; the encryption key is a file here.

| File | What | Synced copy in Infisical |
|---|---|---|
| `client_secret.json` | OAuth app creds | Rebuilt on restore from the three `PERSONAL_GOOGLE_WORKSPACE_*` keys |
| `.encryption_key` | Per-install key wrapping the refresh token | `PERSONAL_GWS_ENCRYPTION_KEY` |
| `credentials.<b64-email>.enc` | Encrypted OAuth refresh token | `PERSONAL_GWS_CREDENTIALS_<KEY_SUFFIX>_ENC_B64` |
| `accounts.json` | Registered accounts list | `PERSONAL_GWS_ACCOUNTS_JSON` |

Infisical is the backup/restore layer, not the runtime dependency: day-to-day `gws` calls never touch Infisical. Only push-after-re-auth and restore-on-new-machine do. The routine push (after every `gws auth login`) syncs the rotating file state headlessly; the stable Keychain key (xdg) is pushed once at interactive setup, where you can approve the Keychain prompt.

## Common Commands

| Command | What it does | Example |
|---|---|---|
| `gws auth status` | Show current auth state | `gws auth status` |
| `gws auth login --account EMAIL` | OAuth login flow (opens browser) | `gws auth login --account you@example.com` |
| `gws <svc> <res> <method> --params '...'` | Generic Google API call | `gws calendar events list --params '{"calendarId":"primary"}'` |
| `gws schema <svc>.<res>.<method>` | Inspect API surface | `gws schema gmail.users.messages.list` |

### Creating drafts / sending with a request body or attachment

Generic write calls (`drafts create`, `messages send`, `messages insert`) need the request body and any media passed through the **right flags** — `--params` is query-string only:

- `--json '<JSON>'` — the request **body** (e.g. the Draft resource: `{"message":{"raw":"<base64url-MIME>","threadId":"..."}}`).
- `--upload <path>` — a local file to attach as **media** (multipart upload).
- `--params '{"userId":"me"}'` — URL/query params only.

Putting the body in `--params` sends an empty body and Google returns **`411 Length Required`**. To draft a reply with an attachment: build a multipart MIME message (text part + attachment part) in code, base64url-encode it as `raw`, set `threadId` (plus `In-Reply-To`/`References` headers) for threading, and pass the whole Draft resource via `--json`. Drafting is always allowed; the *send* stays gated on the operator's code phrase (see the outbound-communications rule).

## When to re-run `gws-push-tokens-to-infisical.sh`

The script at `config/scripts/gws-push-tokens-to-infisical.sh` mirrors the local refresh-token state into Infisical (via your `infisical login` session). Re-run when:

- You re-authenticate (`gws auth login`) — the refresh token changes.
- You add a new Google account to gws — `accounts.json` and `credentials.<new-email>.enc` need pushing. (Multi-account support beyond the primary `email` field in operator-profile is not yet wired through Infisical; one account per operator for now.)
- You rotate the encryption key (rare; happens if you `gws auth logout --all` and re-login).

If you skip the push, local gws keeps working — but Infisical's synced copy goes stale, and the next machine (or state wipe) that restores from it gets a dead token and has to do browser OAuth anyway.

## Scopes — never grant Cloud scopes

> [!warning]
> **Requesting `cloud-platform` or `pubsub` will make you re-authenticate every day** on any Google Workspace org that enforces a Google Cloud reauthentication policy (Admin console → Security → Google Cloud session control). That policy invalidates refresh tokens carrying Cloud scopes on a fixed interval — as short as 1 hour. Because gws bundles every granted scope into one credential, the policy takes Gmail, Drive, and Calendar down with it.

`gws auth login` presents an **interactive scope picker** that lists `Cloud Platform` and `Cloud Pub/Sub` alongside the Workspace services. Two traps:

- `--full` explicitly requests both. Never use it.
- `--services <list>` narrows what the picker *offers* but does **not** reliably strip the Cloud entries — a login with `--services gmail,drive,docs,sheets,calendar` still granted `cloud-platform`.

**Request scopes explicitly instead**, which bypasses the picker entirely:

```bash
gws auth login --scopes \
https://www.googleapis.com/auth/drive,\
https://www.googleapis.com/auth/spreadsheets,\
https://www.googleapis.com/auth/gmail.modify,\
https://www.googleapis.com/auth/calendar,\
https://www.googleapis.com/auth/documents,\
https://www.googleapis.com/auth/presentations,\
openid,\
https://www.googleapis.com/auth/userinfo.email,\
https://www.googleapis.com/auth/userinfo.profile
```

Dropping `cloud-platform` is safe: in the gws binary it appears only in the service-account / application-default-credentials and Model Armor code paths, none of which the Workspace surfaces use.

**Do not request `https://www.googleapis.com/auth/keep`.** It's a restricted scope requiring the Keep API enabled and app verification; without those the consent screen fails outright with *"Access blocked: authorization error."*

### Fixing an account that already has Cloud scopes

1. **Revoke the app first** at https://myaccount.google.com/permissions. This is mandatory, not hygiene — Google returns the **union** of previously-granted scopes on re-consent, so a narrower request still hands `cloud-platform` back.
2. Re-run `gws auth login --scopes ...` as above.
3. **Delete `~/.config/gws/token_cache.json`.** Stale pre-revocation access tokens survive there and produce a confusing split failure: Drive keeps working while Calendar and Gmail return `Request had invalid authentication credentials`. The refresh token is fine; the cache is the problem.
4. Verify with `gws auth status` that the scope list contains no `cloud-platform` or `pubsub`, then run `gws-push-tokens-to-infisical.sh`.

An independent confirmation that the org enforces this policy: `gcloud auth print-access-token` fails with `Reauthentication failed. cannot prompt during non-interactive execution.`

## Trust boundary

`PERSONAL_GWS_ENCRYPTION_KEY` + `PERSONAL_GWS_CREDENTIALS_<KEY_SUFFIX>_ENC_B64` together are equivalent to plaintext access to your Gmail/Drive/Calendar. Anyone with read access to these two Infisical keys can impersonate your Workspace identity. Scope your personal Infisical project accordingly — it should be readable by you alone, never shared with contractors or client projects.

## Known Limitations

- **Pushes need a live Infisical session.** If your `infisical login` session has expired, push scripts log `FAILED to push` to `system/log/gws-push.log` and keep going — local gws is unaffected. Re-run `infisical login`, then the push.
- **Multi-account gws not yet wired through Infisical.** The sync covers the primary `email` from operator-profile only. Multi-account requires additional `PERSONAL_GWS_CREDENTIALS_<SUFFIX>_ENC_B64` keys and a push/restore extension.

## Common Mistakes

- **Re-authenticating without re-running `gws-push-tokens-to-infisical.sh`.** Local state gets the new token, but Infisical still has the old one — a future restore hands back a dead token. Always pair `gws auth login` with the push script.
- **Setting `GOOGLE_WORKSPACE_CLI_CLIENT_ID` permanently in `~/.zshrc` instead of via the wrapper.** Puts the value in plaintext in your shell history and dotfiles. Use the wrapper at `config/shell/gws-env.sh`.
- **Treating your gws state directory as disposable** (`~/.config/gws/` on current installs, `~/Library/Application Support/gws/` on legacy). It's the only live copy of your auth state — and on the xdg layout the encryption key lives in the macOS Keychain (`gws-cli`), not in that directory, so a directory backup alone is incomplete. Infisical holds a synced backup only as current as the last successful push. Check `system/log/gws-push.log` before wiping anything.
- **Passing a request body in `--params`.** `--params` is query-only; the body goes in `--json` (and media in `--upload`). Body-in-`--params` returns `411 Length Required`. Bit us building a Gmail draft-with-attachment on 2026-07-21.
- **Trusting `gws auth status`/`gws auth export` as proof of auth.** They can report `storage: none` / "no encrypted credentials found" while ordinary calls authenticate fine, because the credential is stored per-account (`credentials.<b64email>.enc`) and those subcommands look at the non-account-specific path. Confirm with a real read (`gws calendar +agenda --today`) before concluding auth is broken.
- **Accepting the scope picker's defaults, or reaching for `--full`.** Granting `cloud-platform`/`pubsub` subjects the whole credential to the org's Google Cloud reauth policy — the cause of "I have to log into gws every morning." See § Scopes above. Diagnosed 2026-07-31.
- **Chasing a dead refresh token when only the access-token cache is stale.** After a revoke + re-login, `~/.config/gws/token_cache.json` can still hold tokens for the old scope set, so *some* services authenticate and others don't. Delete the cache before concluding the credential is broken.

## Detection clause

Surface proactively when:

- The operator references something only Google can answer (calendar event, email, Drive doc) and `gws auth status` would resolve it — propose using gws instead of guessing.
- The operator says they re-authenticated gws but didn't push tokens — remind them to run `gws-push-tokens-to-infisical.sh`.
- A new Google account needs adding — note that multi-account isn't wired yet and explain the extension path (new `PERSONAL_GWS_CREDENTIALS_<NEW_SUFFIX>_ENC_B64` key + push/restore support).
- `gws auth status` shows "not authenticated" on a machine that used to work — check whether your gws state directory (`~/.config/gws/` on current installs, else `~/Library/Application Support/gws/`) still has its state files; if missing, run `setup-gws.sh` to restore from Infisical.
- `~/Library/Application Support/gws` turns out to be a symlink to `/Volumes/wd-ramdisk/` — that's the retired pre-2026-07 layout; run `setup-gws.sh` to repair it.
- **The operator mentions re-authenticating gws daily, or more than once a week.** Don't debug the token — check `gws auth status` for `cloud-platform`/`pubsub` in the scope list. If present, that's the cause; walk § Scopes → *Fixing an account that already has Cloud scopes*.
- Some gws services authenticate while others return `invalid authentication credentials` right after a re-login — delete `~/.config/gws/token_cache.json` before investigating further.
